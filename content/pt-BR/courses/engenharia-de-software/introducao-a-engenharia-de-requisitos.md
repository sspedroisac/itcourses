# Introdução à Engenharia de Requisitos

## 1. O que é Engenharia de Requisitos

A **Engenharia de Requisitos** é a área da Engenharia de Software responsável por identificar, compreender, documentar, validar e gerenciar as necessidades e expectativas relacionadas a um sistema.

Seu objetivo é garantir que o software desenvolvido realmente atenda às necessidades dos usuários, clientes e demais envolvidos no projeto.

Antes de construir uma solução, é necessário entender **qual problema precisa ser resolvido** e **quais resultados são esperados**.

---

## 2. O que são Requisitos

Um **requisito** é uma necessidade, capacidade, condição ou restrição que um sistema deve atender.

Os requisitos descrevem **o que o sistema deve fazer** e **quais características ele deve possuir**.

### 2.1 Exemplo

Imagine um sistema de vendas.

Alguns requisitos podem ser:

- O sistema deve permitir o cadastro de clientes;
- O sistema deve permitir a realização de pedidos;
- O sistema deve calcular o valor total da compra;
- O sistema deve permitir o pagamento com cartão;
- O sistema deve responder às operações em até 2 segundos.

Esses requisitos servem como referência para o desenvolvimento e posteriormente para a validação do sistema.

---

## 3. Objetivos da Engenharia de Requisitos

A Engenharia de Requisitos busca:

- Compreender as necessidades dos usuários;
- Identificar os problemas que precisam ser resolvidos;
- Definir claramente o que o sistema deve fazer;
- Registrar requisitos de forma organizada;
- Reduzir ambiguidades e interpretações incorretas;
- Validar se os requisitos estão corretos;
- Gerenciar mudanças durante o projeto;
- Garantir que o produto final atenda às necessidades identificadas.

Uma boa Engenharia de Requisitos ajuda a reduzir retrabalho e problemas durante o desenvolvimento.

---

## 4. Importância da Engenharia de Requisitos

Um dos principais problemas no desenvolvimento de software é construir corretamente uma solução que **não resolve o problema certo**.

Quando os requisitos são mal compreendidos, podem surgir problemas como:

- Funcionalidades desnecessárias;
- Funcionalidades importantes não implementadas;
- Retrabalho;
- Aumento de custos;
- Atrasos no projeto;
- Conflitos entre stakeholders;
- Insatisfação dos usuários;
- Falhas no produto final.

Por isso, a Engenharia de Requisitos funciona como uma ponte entre as **necessidades do negócio** e a **solução de software**.

---

## 5. Stakeholders

Os **stakeholders** são pessoas ou organizações que possuem interesse, influência ou são afetadas pelo sistema.

Eles podem fornecer informações importantes para a identificação dos requisitos.

Exemplos:

- Clientes;
- Usuários finais;
- Gestores;
- Desenvolvedores;
- Analistas;
- Administradores;
- Órgãos reguladores;
- Proprietários do negócio.

Cada stakeholder pode possuir necessidades e perspectivas diferentes.

Por isso, é importante identificar os envolvidos e compreender suas expectativas.

---

## 6. Processo de Engenharia de Requisitos

A Engenharia de Requisitos pode ser organizada em diferentes atividades.

Um fluxo comum envolve:

```text
Elicitação
    │
    ▼
Análise
    │
    ▼
Especificação
    │
    ▼
Validação
    │
    ▼
Gerenciamento
```

Essas atividades não precisam acontecer necessariamente de forma totalmente linear.

À medida que novas informações são descobertas, os requisitos podem ser revisados e modificados.

---

## 7. Características de um Bom Requisito

Um bom requisito deve ser:

- **Claro:** deve ser facilmente compreendido;
- **Não ambíguo:** deve possuir apenas uma interpretação;
- **Completo:** deve conter informações suficientes;
- **Consistente:** não deve entrar em conflito com outros requisitos;
- **Viável:** deve ser possível de implementar;
- **Testável:** deve ser possível verificar se foi atendido;
- **Rastreável:** deve ser possível acompanhar sua origem e implementação.

Essas características ajudam a transformar necessidades abstratas em especificações que podem orientar o desenvolvimento.

---

## 8. Exemplo Prático

Imagine que uma empresa deseja desenvolver um sistema de atendimento ao cliente.

Durante uma entrevista, um usuário informa:

> "Precisamos que o atendimento seja rápido."

Essa informação representa uma necessidade, mas ainda não é um bom requisito.

Após análise, a equipe pode transformar essa necessidade em algo mais específico:

> "O sistema deve permitir que um atendente localize um cliente pelo CPF."

E também:

> "A consulta de clientes deve retornar os resultados em até 2 segundos."

O primeiro requisito descreve uma **funcionalidade**.

O segundo estabelece uma característica de **desempenho**.

Assim, a Engenharia de Requisitos ajuda a transformar necessidades vagas em requisitos que podem ser compreendidos, implementados e testados.

---

## 9. Requisitos e Desenvolvimento de Software

Os requisitos servem como base para diversas atividades do desenvolvimento.

```text
Necessidades do negócio
          │
          ▼
      Requisitos
          │
          ▼
       Projeto
          │
          ▼
   Implementação
          │
          ▼
        Testes
          │
          ▼
        Produto
```

Quando os requisitos são bem definidos, as demais etapas possuem uma referência mais clara para orientar suas decisões.

---

## 10. Boas Práticas

- Envolver os stakeholders durante a definição dos requisitos;
- Evitar requisitos ambíguos;
- Utilizar linguagem clara e objetiva;
- Diferenciar requisitos funcionais e não funcionais;
- Validar os requisitos antes da implementação;
- Priorizar requisitos de acordo com seu valor;
- Registrar mudanças nos requisitos;
- Garantir que os requisitos sejam testáveis;
- Manter rastreabilidade durante o desenvolvimento.

---

## 12. Conclusão

A **Engenharia de Requisitos** é uma etapa fundamental da Engenharia de Software porque estabelece uma compreensão compartilhada sobre o que precisa ser desenvolvido.

Por meio da **elicitação**, **análise**, **especificação**, **validação** e **gerenciamento**, é possível transformar necessidades dos stakeholders em requisitos claros e verificáveis.

Quanto melhor os requisitos forem compreendidos e gerenciados, maiores são as chances de o software desenvolvido realmente resolver o problema para o qual foi criado.
